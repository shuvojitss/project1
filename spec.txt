# Infy_SupplyChain360 — Enterprise Build Specification

This document is a single, continuously numbered build guide. Read and implement it in order. Items 1–10 fix the rules, items 11–40 define the backend, items 41–58 define the frontend, data, messaging, quality and operations, and items 59–75 give the implementation roadmap and acceptance checks. Every item is a binding requirement unless it says "optional".

1. **Product vision.** Infy_SupplyChain360 is an end-to-end supply chain platform giving visibility and control over procurement, inventory, supplier collaboration, warehouse operations, order fulfilment and distribution across geographically distributed locations. Goals: reduce operational inefficiency, raise inventory accuracy, optimise logistics cost and lead time, and improve resilience when a supplier, warehouse or carrier fails.

2. **Locked technology stack.** Nothing outside this list may be introduced.
    - Frontend: React 18, TypeScript 5 (strict mode), Bootstrap 5 (via `react-bootstrap` and `bootstrap`), Vite as build tool.
    - Frontend supporting libraries (only these): `react-router-dom`, `axios`, `recharts` (charts).
    - Backend: Java 17, Spring Boot 3.x per service, with Spring Web, Spring Data JPA, Spring Security, Spring AMQP, Spring Validation, Spring Boot Actuator, Spring Cloud Gateway, Spring Cloud Netflix Eureka, Spring Cloud OpenFeign, Resilience4j, Flyway, springdoc-openapi, Spring Mail.
    - Database: MySQL 8 (InnoDB, utf8mb4).
    - Messaging: RabbitMQ 3.13 (AMQP 0-9-1).
    - Build tooling (not runtime stack): Maven, plus plain shell scripts for local startup. Services run directly from executable JARs, with no containers.
    - Test tooling: JUnit 5, Mockito, Vitest, React Testing Library. Integration tests run against a locally installed MySQL 8 and RabbitMQ (dedicated `_test` schemas and the `scm360_test` vhost).
    - Explicitly forbidden: Docker or any container tooling (including Docker Compose and Testcontainers), Kafka, Redis, MongoDB, Elasticsearch, GraphQL, gRPC, any other UI kit (MUI, Ant Design, Tailwind), any other message broker or database.

3. **Non-negotiable microservice rules.**
    - One service = one bounded context = one Spring Boot application = one independently deployable unit = one MySQL schema with its own credentials.
    - No shared database, no cross-schema joins, no foreign keys across services. Services reference each other's data by UUID only.
    - No shared domain libraries or shared JPA entities. The only permitted shared artifact is `scm360-common-starter`, a Spring Boot starter containing cross-cutting code only (JWT filter, correlation-ID filter, error format, event envelope class, outbox base classes). It must contain zero business logic.
    - The browser talks only to the API Gateway. Services never expose ports to the browser directly.
    - State changes propagate between services through RabbitMQ events. Synchronous REST between services is allowed only for read queries that need an immediate answer, must go through OpenFeign with timeout and circuit breaker, and must have a documented fallback.
    - Each service keeps small local reference copies (for example `product_ref`, `supplier_ref`, `warehouse_ref`) updated by events, so it can run when other services are down.
    - Every service must build, test, start and deploy on its own.

7. **Internal package layout for every service** (base package `com.infy.scm360.<service>`): `controller`, `service`, `domain` (entities, enums, state machines), `repository`, `messaging` (publishers, listeners, outbox), `client` (Feign), `config`, `dto`, `mapper`, `exception`. Controllers contain no business logic, entities are never returned from controllers, DTOs are Java records, and all business rules live in `service` and `domain`.

8. **Naming conventions.** Services: `kebab-case`. Java: standard conventions. REST paths: `/api/v1/<plural-noun>`. Tables: `snake_case` plural. Exchanges: `<domain>.events`. Routing keys: `<domain>.<entity>.<past-tense-verb>` (for example `inventory.stock.reserved`). Queues: `<consumer-service>.<producer-domain>.<purpose>`. Branches: `feature/<service>-<topic>`. Commits: Conventional Commits.

9. **Identity service.**
    - Entities: `users`, `roles`, `user_roles`, `user_locations` (which warehouses/regions a user may act on), `refresh_tokens`, `audit_log`.
    - Endpoints: `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `GET /api/v1/users/me`, CRUD on `/api/v1/users` (ADMIN only), `PUT /api/v1/users/{id}/roles`, `PUT /api/v1/users/{id}/locations`.
    - Passwords hashed with BCrypt (strength 12). Access token JWT lifetime 15 minutes, refresh token 7 days, rotated on every use and revocable.
    - JWT claims: `sub` (user UUID), `roles`, `locationIds`, `supplierId` (only for supplier users), `iat`, `exp`. Sign with RS256; identity holds the private key, all other services hold only the public key.
    - Account lockout after 5 failed logins for 15 minutes. Every login, role change and lockout is written to `audit_log`.

11. **API Gateway.**
    - Spring Cloud Gateway with routes `lb://<service-name>` for each service under `/api/v1/**`, path-prefix mapped (for example `/api/v1/orders/**` to order-service).
    - Validates the JWT signature and expiry, rejects unauthenticated requests except `/api/v1/auth/login` and `/api/v1/auth/refresh`, then forwards `X-User-Id`, `X-User-Roles`, `X-Location-Ids` and `X-Correlation-Id` (generated if absent).
    - Downstream services must still validate the JWT themselves via the common starter (defence in depth). Headers are convenience only and never the sole trust source.
    - Configure CORS for the frontend origin only. Add a global fallback response (503 with the standard error body) when a route's circuit breaker is open.

12. **Discovery server.** Spring Cloud Netflix Eureka server in standalone mode for development. Every service registers with its `spring.application.name`. Health checks use Actuator `/actuator/health`.

13. **Catalog service.**
    - Entities: `product` (sku unique, name, description, category_id, uom, weight, dimensions, unit_cost, status, version), `category` (tree via `parent_id`), `unit_of_measure`.
    - Endpoints: CRUD under `/api/v1/products` and `/api/v1/categories`, search by sku/name/category with pagination.
    - Events published: `catalog.product.created`, `catalog.product.updated`, `catalog.product.discontinued`. Inventory, procurement, warehouse and order services keep `product_ref` copies.

14. **Supplier service.**
    - Entities: `supplier` (code, legal_name, tax_id, status: PENDING, APPROVED, SUSPENDED, BLACKLISTED), `supplier_contact`, `supplier_document` (metadata only, file stored on local disk volume with path in DB), `supplier_contract`, `supplier_item` (product reference, lead time, price, MOQ), `supplier_scorecard`, `asn` (advance shipment notice) and `asn_line`.
    - Onboarding workflow: submit, document check, risk review, approval by PROCUREMENT_MANAGER. Approval creates a SUPPLIER_USER invitation via event to identity-service.
    - Scorecard computed from events: on-time delivery rate, quality (rejected quantity ratio), lead-time variance, responsiveness (PO acknowledgement time). Recalculated on every `warehouse.goods.received` event. Score 0–100 with configurable weights.
    - Supplier portal endpoints (role SUPPLIER_USER, data limited to own `supplierId` claim): view POs, acknowledge or reject PO, submit ASN, view own scorecard.
    - Events published: `supplier.approved`, `supplier.suspended`, `supplier.scorecard.updated`, `supplier.po.acknowledged`, `supplier.asn.submitted`.

15. **Procurement service.**
    - Entities: `requisition`, `requisition_line`, `purchase_order`, `po_line`, `approval_step`, `goods_receipt_ref` (local copy of received quantities), `po_status_history`.
    - PO state machine: `DRAFT -> PENDING_APPROVAL -> APPROVED -> ISSUED -> ACKNOWLEDGED -> PARTIALLY_RECEIVED -> RECEIVED -> CLOSED`, with `REJECTED` and `CANCELLED` as terminal branches. Illegal transitions throw a domain exception mapped to HTTP 409.
    - Approval rule table `approval_rule` (amount thresholds mapped to role), for example up to 50,000 by PROCUREMENT_MANAGER and above that requires two approvals. Rules are data, not code.
    - Auto-requisition: consumes `inventory.stock.low` and drafts a requisition using the preferred supplier from `supplier_item_ref`.
    - Receipt matching: on `warehouse.goods.received`, update received quantities, move PO status, flag over- and under-delivery beyond tolerance (default 5%).
    - Events published: `procurement.requisition.created`, `procurement.po.approved`, `procurement.po.issued`, `procurement.po.cancelled`, `procurement.po.closed`.

16. **Inventory service.**
    - Entities: `stock_level` (product_id, warehouse_id, bin_id nullable, on_hand, reserved, available as computed, version), `stock_ledger` (immutable, append-only: movement_type, quantity_delta, reference_type, reference_id, occurred_at), `reservation`, `reorder_rule` (min, max, reorder_point, safety_stock, preferred_supplier_id), `stock_adjustment` (reason, approval).
    - Every change to `stock_level` is written together with a `stock_ledger` row in one transaction. `stock_level` is a projection of the ledger and must be reproducible from it.
    - Concurrency: optimistic locking via `@Version` with bounded retry, plus a conditional update (`UPDATE ... SET reserved = reserved + ? WHERE available >= ?`) so reservations can never oversell.
    - Reservation lifecycle: `RESERVED -> COMMITTED` or `RELEASED` (cancel or timeout after configurable TTL, default 24 h, released by a scheduled job).
    - Low-stock check after each movement: if `available <= reorder_point` publish `inventory.stock.low` (debounced to once per product and warehouse per 24 h).
    - Events published: `inventory.stock.changed`, `inventory.stock.low`, `inventory.stock.reserved`, `inventory.reservation.failed`, `inventory.reservation.released`, `inventory.stock.adjusted`.

17. **Warehouse service.**
    - Entities: `warehouse` (code, name, region, address, capacity), `zone`, `bin`, `inbound_receipt`, `receipt_line`, `putaway_task`, `pick_list`, `pick_line`, `pack_task`, `transfer_order`, `cycle_count`, `cycle_count_line`.
    - Inbound flow: expected receipts are created from `procurement.po.issued` and `supplier.asn.submitted`. Operator receives (with accepted, rejected and damaged quantities), the system generates putaway tasks to suggested bins (rule: same product bin first, then free bin in the right zone).
    - Outbound flow: on `order.confirmed` generate a pick list (FIFO by receipt date, optional FEFO when expiry exists), then pack task, then publish `warehouse.order.packed`.
    - Transfers between warehouses: `DRAFT -> DISPATCHED -> IN_TRANSIT -> RECEIVED`, with inventory moves triggered by events.
    - Cycle counts: manager creates a count, operators submit counted quantities, variance above threshold goes to approval, approval publishes `warehouse.count.variance.approved` which inventory turns into an adjustment.
    - Events published: `warehouse.goods.received`, `warehouse.putaway.completed`, `warehouse.order.picked`, `warehouse.order.packed`, `warehouse.transfer.dispatched`, `warehouse.transfer.received`, `warehouse.count.variance.approved`.

18. **Order service.**
    - Entities: `customer_order`, `order_line`, `order_status_history`, `customer_ref` (name, ship-to address, customer is a simple embedded concept here, no separate CRM service), `backorder`.
    - Order state machine: `CREATED -> RESERVING -> CONFIRMED -> PICKING -> PACKED -> SHIPPED -> DELIVERED`, plus `BACKORDERED`, `REJECTED`, `CANCELLED`. Cancellation allowed until `PACKED`.
    - Order service is the saga coordinator for fulfilment (see item 52). It owns order status only; stock, picking and shipment data stay in their own services.
    - Endpoints: `POST /api/v1/orders`, `GET /api/v1/orders`, `GET /api/v1/orders/{id}`, `POST /api/v1/orders/{id}/cancel`, `GET /api/v1/orders/{id}/timeline`.
    - Events published: `order.placed`, `order.confirmed`, `order.backordered`, `order.cancelled`, `order.shipped`, `order.delivered`.

19. **Transportation service.**
    - Entities: `carrier` (name, modes, service levels, rate card), `rate_card_entry` (origin region, destination region, mode, rate per kg, per km, minimum), `shipment`, `shipment_leg`, `shipment_item`, `tracking_event`, `proof_of_delivery`, `vehicle` (optional), `route_plan`.
    - Shipment state machine: `PLANNED -> ASSIGNED -> DISPATCHED -> IN_TRANSIT -> DELIVERED`, plus `DELAYED`, `FAILED_DELIVERY`, `CANCELLED`.
    - Planning: on `warehouse.order.packed` create a shipment; planner (or auto-rule) selects carrier by lowest cost meeting required delivery date using `rate_card_entry`. Consolidation of shipments with same origin, destination region and date is supported.
    - Tracking: planners or carrier users post `tracking_event`s; ETA breach marks shipment `DELAYED` via a scheduled job.
    - Events published: `transport.shipment.created`, `transport.shipment.dispatched`, `transport.shipment.delayed`, `transport.shipment.delivered`, `transport.delivery.failed`.

20. **Analytics service.**
    - Consumes events from every domain and maintains denormalised read models in `scm_analytics` (for example `fact_order`, `fact_po`, `fact_receipt`, `fact_shipment`, `fact_stock_snapshot`, `dim_product`, `dim_supplier`, `dim_warehouse`, `dim_date`). It never calls other services and never writes back to them.
    - Daily snapshot job stores end-of-day stock per product and warehouse.
    - Dashboard endpoints (all accept `from`, `to`, `warehouseId`, `region` filters): `/api/v1/analytics/kpis`, `/inventory`, `/procurement`, `/suppliers`, `/fulfilment`, `/logistics`.
    - KPI definitions (implement exactly): inventory accuracy = 1 minus absolute count variance divided by counted quantity; stock turnover = cost of goods shipped divided by average inventory value; days of inventory on hand; fill rate = lines fully shipped from first reservation divided by total lines; OTIF = orders delivered on time and in full divided by orders delivered; supplier on-time rate; PO cycle time (created to approved, approved to received); order cycle time (placed to delivered); transport cost per shipment and per kg; warehouse utilisation = used bins divided by total bins; stockout count; backorder rate.
    - Events are idempotent upserts so replaying a queue rebuilds the read models.

21. **Notification service.**
    - Consumes alert-worthy events (low stock, PO approval needed, PO issued to supplier, shipment delayed, delivery failed, cycle count variance, order backordered) and maps each to recipients by role and location using a local `recipient_rule` table.
    - Channels: in-app (stored in `notification`, pushed to the SPA by Server-Sent Events at `/api/v1/notifications/stream`) and email through Spring Mail (SMTP configured by environment variables; in the `dev` profile emails are written to the log instead of being sent).
    - Endpoints: list, mark read, mark all read, unread count, user preferences per channel.

22. **Database rules (all services).**
    - Flyway migrations only (`db/migration/V<n>__<description>.sql`). `spring.jpa.hibernate.ddl-auto=validate` everywhere. Never edit an applied migration.
    - Primary keys: UUID stored as `CHAR(36)`. Money: `DECIMAL(19,4)` plus a `currency` column (ISO 4217). Quantities: `DECIMAL(19,3)`. Timestamps: `DATETIME(6)` stored in UTC.
    - Every table has `created_at`, `created_by`, `updated_at`, `updated_by`, and mutable aggregates have `version BIGINT` for optimistic locking.
    - Soft delete (`deleted_at`) for master data. Transactional data is never deleted.
    - Index every foreign-key-like column and every filter or sort column used by list endpoints. Add composite indexes that match real query patterns (for example `stock_level(product_id, warehouse_id)` unique).
    - Use pagination (`page`, `size`, max 100) on every list endpoint. No unbounded queries.

25. **RabbitMQ topology.**
    - One durable topic exchange per domain: `catalog.events`, `supplier.events`, `procurement.events`, `inventory.events`, `warehouse.events`, `order.events`, `transport.events`.
    - One dead-letter exchange `scm.dlx` (direct). Every consumer queue declares `x-dead-letter-exchange=scm.dlx` and routes to a matching `<queue>.dlq`.
    - Consumer queues are durable, one per consumer service and purpose, bound with specific routing keys (never `#` except in analytics-service, which binds `#` on each domain exchange).
    - Publishers use publisher confirms and `mandatory` flag. Consumers use manual acknowledgement, prefetch 10–20, and concurrency 2–4.
    - Retry: 3 attempts with exponential backoff (1 s, 5 s, 30 s) through Spring AMQP retry interceptor, then reject to the DLQ. A protected admin endpoint in each service can republish a DLQ message after the fix.
    - Messages are persistent JSON with `content-type: application/json`. Queue and exchange declarations are done in code (`Declarables` beans) in each service for the queues it owns.

28. **Transactional outbox implementation.** A service never publishes to RabbitMQ inside the business transaction. Instead: write the business change and an `outbox_event` row in the same MySQL transaction, then a scheduled relay (every 500 ms, batch 100, `SELECT ... FOR UPDATE SKIP LOCKED`) publishes pending rows with publisher confirms, marks them `SENT`, and increments `attempts` on failure (mark `FAILED` after 10 attempts and raise an alert metric). A cleanup job deletes `SENT` rows older than 7 days. This guarantees at-least-once delivery without distributed transactions.

29. **Idempotent consumer implementation.** Every listener runs in one transaction that first inserts `(eventId, consumerName)` into `processed_message`. On duplicate-key the message is acknowledged and skipped. Otherwise the business logic runs and the transaction commits before the ack. Consumers must also tolerate out-of-order events (use `version` or `occurredAt` comparison before overwriting reference data).

30. **Procure-to-stock flow.**
    - Step 1: low stock detected by inventory, so `inventory.stock.low` is published.
    - Step 2: procurement drafts a requisition, officer converts it to a PO, approval rules apply, `procurement.po.approved` and `procurement.po.issued` are published.
    - Step 3: supplier acknowledges in the portal (`supplier.po.acknowledged`) and later submits an ASN.
    - Step 4: warehouse receives goods against the expected receipt, publishes `warehouse.goods.received`.
    - Step 5: inventory increases `on_hand` and writes ledger rows, procurement updates PO status, supplier updates scorecard, analytics updates facts.

31. **Order-to-delivery flow.**
    - Step 1: SALES_COORDINATOR creates an order, order-service stores `CREATED -> RESERVING` and emits `order.placed` through the outbox.
    - Step 2: inventory reserves each line atomically. All lines reserved means `inventory.stock.reserved`, any line short means `inventory.reservation.failed` after releasing partial reservations.
    - Step 3: order becomes `CONFIRMED` (publishes `order.confirmed`) or `BACKORDERED`.
    - Step 4: warehouse creates the pick list, operators pick (`warehouse.order.picked`, inventory commits reservation to on-hand deduction) and pack (`warehouse.order.packed`).
    - Step 5: transport creates a shipment, assigns a carrier, dispatches (`transport.shipment.dispatched`), order becomes `SHIPPED`.
    - Step 6: delivery with proof of delivery publishes `transport.shipment.delivered`, order becomes `DELIVERED`.

32. **Saga and compensation rules (choreography with order-service as owner of the business state).**
    - Reservation failure: order moves to `BACKORDERED`, a `backorder` row is created, no stock stays reserved.
    - Cancellation before pack: `order.cancelled` makes inventory release reservations, warehouse cancel open pick tasks, transport cancel planned shipments.
    - Failed delivery: `transport.delivery.failed` moves the order to a `DELIVERY_EXCEPTION` flag for planner action, stock is not auto-returned until a return is processed.
    - Reservation timeout: scheduled job releases expired reservations and publishes `inventory.reservation.released`, order-service reacts by moving the order to `BACKORDERED`.
    - Every saga step is idempotent and every compensation is safe to run twice.
